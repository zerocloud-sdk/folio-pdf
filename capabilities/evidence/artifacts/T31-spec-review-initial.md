Initial independent Spec review — two P2 correctness findings. Final gate remains open.

1. **P2 — PDF417 RAW loses byte-compaction state at ECI.** The profile requires “malformed raw words” to return stable checked failures, and the [contract](../../../docs/two-dimensional-barcodes.md#pdf417) admits complete 901/924 byte and 927 ECI sequences while rejecting invalid byte groups. In `pdf-document/src/main/java/net/zerocloud/pdf/BarcodePdf417Raw.java:25–31`, scanning stops at 927 and subsequent data is validated as text. Both execution profiles publish `[901,65,927,26,300]`; independent ZXing decoding yields `A,`, truncating the invalid byte 300 to 44. `[924,0,0,0,0,0,927,26,300]` also publishes. Conversely, valid `[901,927,26,65]` is rejected. Preserve byte-compaction state and validate ECI-separated groups; cover accepted/rejected boundaries through public Workflow tests.

2. **P2 — DataMatrix RAW sizing changes EDIFACT payloads.** The [contract](../../../docs/two-dimensional-barcodes.md#datamatrix-ecc200) requires “supported complete … EDIFACT … sequences ending in ASCII state.” `BarcodeDataMatrixCompaction.java:13–14` bypasses capacity-sensitive handling for RAW, while `BarcodeDataMatrixRaw.java:63–72` validates explicit EDIFACT termination without the selected symbol capacity. In both profiles, `rawDataMatrix(240,5,240)` automatically selects 10×10 and decodes as U+0004; the identical words at 12×12 decode as `A`. With two words remaining, EDIFACT implicitly resumes ASCII. Automatic sizing must preserve the supplied stream; an incompatible fixed capacity must fail before publication.
